    MedGemma 개요 및 아키텍처¶

    📌 개요¶

    MedGemma는 Google-Health가 개발한 4B/27B 멀티모달 LLM으로, 의료 영상 텍스트 분석을 최적화했다.

    모델 버전¶

    버전 크기 유형 주요 용도 GPU 요구사항
    MedGemma 4B 4B 멀티모달 (이미지+텍스트) 의료 이미지 분석 4090 int4 / A100 fp16
    MedGemma 27B 27B 텍스트 전용 판독문 분석, EHR 탐색 A100 int4 / 80GB A100 fp16

    특징¶

    • ✅ 멀티모달: CT, MRI, 병리 슬라이드 등 다양한 의료 영상 지원
    • ✅ 임상 통합: FHIR/EHR 표준, DICOMweb 지원
    • ✅ 평판 모델: 식약처 인증 SmartEndo, Auto CTR 등 실제 임상 적용
    • ✅ 오픈 소스: Hugging Face, Vertex AI 배포 가능

    핵심 컴포넌트¶

    컴포넌트 역할 설명
    Vision Encoder 이미지 표현 학습 SigLIP 모델로 의료 이미지 특징 추출
    Text Decoder 텍스트 생성 LLaMA 기반 디코더로 프롬프트 처리
    Cross-Modal Attention 멀티모달 통합 이미지 표현 + 텍스트 프롬프트 결합
    Projection 공간 변환 임베딩 차원 매핑

    🧠 배경 지식 (Background Knowledge)¶

    1. 멀티모달 LLM이란?¶

    개념: 하나의 모델이 텍스트와 이미지를 동시에 이해하고 처리할 수 있는 AI 모델

    의료 도메인에서의 중요성: - 의료 영상 (X-ray, CT, MRI) + 판독문 분석 - 시각적 정보 + 서술적 정보 통합 이해 - 단일 모델로 멀티모달 작업 수행

    기존 방식 vs 멀티모달: 

    기존 방식:
  의료 영상 → AI (독립) → 결과
  판독문 → LLM (독립) → 결과

멀티모달:
  의료 영상 + 판독문 → MedGemma (통합) → 종합 분석

    2. SigLIP (Sign Language Learning Image Pairs)¶

    개념: 이미지와 텍스트 쌍을 학습하여 임베딩 공간에서 최대한 유사한 쌍을 유지하는 모델

    의료 영상에서의 장점: - 비정형 의료 이미지도 잘 표현 가능 - 관련 이미지 간 유사성 학습 - 256x256 패치 기반 처리

    작동 방식: 

    # 예시: 의료 이미지 임베딩
image1 = "폐결절 있는 흉부 X-ray"
image2 = "비슷한 크기의 결절 있는 흉부 X-ray"

# 모델은 image1과 image2를 유사하게 임베딩
embedding1 ≈ embedding2

# 반면:
image3 = "정상 흉부 X-ray"
embedding3 → 구별됨

    3. FHIR (Fast Healthcare Interoperability Resources)¶

    개념: 의료 데이터를 표준화하여 다른 시스템 간 교환하기 위한 표준

    주요 리소스: - Patient: 환자 정보 - Observation: 검사 결과 (혈압, 혈당 등) - Condition: 진단 정보 - Medication: 약물 처방

    사용 사례: 

    // Patient: 환자 정보
{
  "resourceType": "Patient",
  "name": [{"family": "김", "given": ["철수"]}],
  "birthDate": "1970-01-01",
  "gender": "male"
}

// Observation: 혈압 검사 결과
{
  "resourceType": "Observation",
  "code": {"coding": [{"code": "8480-6", "display": "Systolic BP"}]},
  "valueQuantity": {"value": 120, "unit": "mmHg"}
}

    4. DICOMweb (DICOM 표준의 웹 기반 버전)¶

    개념: DICOM 의료 영상을 웹 기반으로 접근할 수 있는 프로토콜

    특징: - HTTP 기반 API (GET, POST) - RESTful 디자인 - 웹 브라우저 및 클라이언트 앱에서 접근 가능

    주요 엔드포인트: 

    /studies/{study_uid}           - 전체 스터디
/studies/{study_uid}/instances - 특정 이미지 인스턴스
/instances/{instance_uid}/frame - 특정 프레임

    사용 예시: 

    # DICOMweb API로 이미지 조회
response = requests.get(
    "https://pacs.example.com/dicomweb/studies/1.2.3.4/instances/1.2.3.5"
)
image_data = response.content  # DICOM 파일

    5. QLoRA (Quantized Low-Rank Adaptation)¶

    개념: 모델 전체를 학습하는 대신, 양자화된 얇은 레이어만 학습하는 효율적인 파인튜닝 방법

    작동 원리: 

    기존 파인튜닝 (파라미터 개수 증가):
  Base Model (10B) → Fine-tuned Model (12B)
  ⚠️ 전체 가중치 학습 → 메모리 부족

QLoRA (가중치 줄이고 학습):
  Base Model (10B) → LoRA 어댑터 (0.1B) + 양자화된 모델
  ✅ 어댑터만 학습 → 메모리 효율적

    장점: - A100 40GB로 4B 모델 파인튜닝 가능 - 학습 시간 3-5배 단축 - 저장 공간 최소화

    학습 포인트: 

    # QLoRA 설정 예시
from peft import LoraConfig

lora_config = LoraConfig(
    r=16,              # Rank (양자화 레이어의 차원)
    lora_alpha=32,     # 학습률 조정
    target_modules=[   # 어댑터 적용 대상
        "q_proj", "v_proj"
    ],
    lora_dropout=0.05  # Dropout 비율
)

    🚀 실행 전략 (Our Lab Strategy)¶

    1단계: 4090 기본 테스트¶

    목표: 최소 사양으로 모델 동작 확인

    모델 GPU 양자화 예상 메모리 목표
    MedGemma 4B RTX 4090 int4 ~18GB ✅ 추론 가능
    MedGemma 27B RTX 5090 int4 ~24GB ✅ 추론 가능

    실행 플로우: 

    1. Google-Health GitHub에서 모델 확인
   https://github.com/Google-Health/medgemma

2. Hugging Face에서 다운로드
   https://huggingface.co/google/medgemma-4b-it

3. 4090에서 int4 양자화로 실행
   - 추론 테스트 (quick_start.ipynb)
   - 병리 슬라이드 분석 테스트
   - 판독문 비식별화 테스트

4. 성능 측정 (소요 시간, 정확도)

    2단계: A100 서빙¶

    목표: 다중 사용자 서빙 및 파인튜닝

    작업 GPU 예상 메모리 목표
    추론 (4B) A100 40GB ~16GB (fp16) ✅ 여러 사용자
    추론 (27B) A100 80GB ~52GB (fp16) ✅ 여러 사용자
    파인튜닝 (4B) A100 40GB ~35GB (QLoRA) ✅ 커스터마이징
    파인튜닝 (27B) A100 80GB ~65GB (QLoRA) ✅ 커스터마이징

    실행 플로우: 

    1. A100에서 fp16 기본 추론 테스트
   - 4B 모델: A100 40GB → 서빙 가능
   - 27B 모델: A100 80GB → 서빙 가능

2. Vertex AI 배포 (엔드포인트 생성)
   - 온라인 추론 엔드포인트
   - 배치 처리 엔드포인트

3. API 개발
   - REST API (HF transformers)
   - GraphQL (FHIR 리소스)
   - DICOMweb Proxy

4. 다중 사용자 테스트
   - 부하 테스트 (Concurrent requests)
   - 비용 모니터링

    3단계: 커스터마이징¶

    목표: 우리 연구실 맞춤형 모델 개발

    1. 데이터셋 준비
   - 우리 연구실 데이터 (SmartEndo, Auto CTR 등)
   - 다른 연구실 데이터 (FHIR/EHR)

2. 파인튜닝
   - A100에서 QLoRA/SFT
   - RLHF/GRPO로 고급 튜닝

3. 배포 및 운영
   - 엔드포인트 모니터링
   - 성능 추적
   - 정기 업데이트
