    04. 모델 다이어트: 최적화와 양자화 (Optimization & Quantization)¶

    집사야! 지금까지 우리는 모델을 ONNX로 변환(Trace)하고, 엔진(ORT)으로 돌리는 법까지 배웠어. 하지만 진짜 ONNX를 쓰는 이유는 지금부터야. 바로 "모델을 더 가볍고 빠르게 만드는 마법"이지! 🐱✨

    1. 그래프 최적화 (Graph Optimization)¶

    ONNX Runtime은 추론을 시작하기 전에 모델 그래프를 쓱 훑어보고 청소를 해줘.

    🧹 불필요한 연산 정리 (Constant Folding)¶

    • 상황: a = 3, b = 2, c = a + b 라는 노드가 있다고 치자.
    • 최적화 전: 실행할 때마다 3+2를 계산함.
    • 최적화 후: 그냥 c = 5라는 상수 노드로 바꿔버림! (계산 비용 0)

    🔗 연산 융합 (Operator Fusion)¶

    • 상황: Conv -> BatchNormalization -> Relu 처럼 자주 붙어 다니는 삼총사들이 있어.
    • 최적화 전: 메모리에서 데이터를 3번이나 읽고 써야 해. (느림 🐢)
    • 최적화 후: ConvBnRelu라는 하나의 거대한 커널로 합쳐서 한 번에 처리해! (빠름 🚀)

    💡 Tip: sess_options.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL 옵션을 켜면 이 모든 마법이 자동으로 일어나!

    2. 양자화 (Quantization) - 핵심 기술!¶

    모델의 정밀도(Precision)를 낮춰서 속도를 올리는 기술이야. 마치 "소수점 10자리까지 계산하던 걸, 반올림해서 정수로 계산하자!"라는 거지.

    ⚖️ FP32 vs INT8¶

    • FP32 (32-bit Float): 정밀하지만 무겁고 느려. (대부분의 모델 기본값)
    • INT8 (8-bit Integer): 표현할 수 있는 숫자는 적지만, 용량은 1/4, 속도는 2~4배 빨라져!

    📊 양자화의 두 가지 방식¶

    방식 설명 장점 단점
    Dynamic Quantization 실행될 때(Runtime) 입력 데이터 범위를 보고 변환 빠르고 간편함 (보정 데이터 불필요) 최적화 효과가 조금 덜함
    Static Quantization 미리 샘플 데이터(Calibration)를 보고 범위를 고정 최고의 성능 (가장 빠름) 준비 과정이 복잡함

    🛠️ 실습: GLiNER 모델 다이어트 시키기¶

    from onnxruntime.quantization import quantize_dynamic, QuantType

model_fp32 = 'model.onnx'
model_quant = 'model.quant.onnx'

# 한 줄로 끝나는 다이어트!
quantize_dynamic(
    model_input=model_fp32,
    model_output=model_quant,
    weight_type=QuantType.QUInt8  # 가중치를 8비트 정수로 변환
)

print(f"🎉 변환 완료! {model_quant} 생성됨.")

    이렇게 하면 파일 크기가 400MB → 100MB로 확 줄어드는 기적을 볼 수 있어! 🎈
